# 发布和回退

发布单位是后端、控制台、设备工具、数据库迁移与相匹配的基础服务配置。当前单实例 SQLite 部署需要短维护窗口；不提供滚动多副本的承诺。

## 发布前

1. 记录实际运行的 Git 提交及两个容器的 image ID/digest，不只记录会被覆盖的 `latest`。保留旧镜像或能重建它的对应源码/锁文件。
2. 在隔离预发布环境运行 `deployment_check.py config` 和 `acceptance`；检查输出中的 `failed` 与 `pending`，为真实通行证、SMTP、AI、SQL/S3 和业务流程保留单独验收证据。
3. 运行当前提交的 Go、前端、浏览器、真实 SQL/S3 集成与备份恢复测试。比较当前迁移和待部署迁移，不对不可逆变更猜测“旧版应该也能读”。
4. 执行跨本机/SQL/S3 的协调备份；在新目录或新卷完成恢复演练，并保留独立主密钥。记录可接受的数据损失窗口、实测恢复耗时和回退负责人。
5. 预先构建新镜像，检查磁盘容量。通过受控反向代理挂维护页，冻结新写入、直连 SQL/S3 客户端和设备任务，再切换镜像。

仓库部署使用源码构建，更新时可在一个独立 checkout 中固定批准的提交，避免运行目录存在未审查修改：

```sh
# 在固定提交的 checkout 中，私密配置按部署流程复制，绝不提交到 Git。
cd deploy/app-cloud
docker compose --env-file .env config --quiet
docker compose --env-file .env build app-cloud console maintenance
# 按 RECOVERY.md 完成维护窗口内协调备份，然后更新。
docker compose --env-file .env up -d --no-build app-cloud console
```

不要执行 `docker compose down --volumes`。不要让旧、新后端同时写同一个卷。不同 checkout 使用相同 Compose 项目名和明确数据卷时才代表更新同一部署；预发布应使用独立项目名与卷。

## 发布后

- 检查 `/healthz`、`/readyz` 和独立受保护的 `/ops/diagnostics`。`/ops/metrics` 由受控监控程序以独立运营 token 读取；这个 token 不授予用户或业务权限。
- 完成真实登录/退出，确认项目和应用启用状态，执行一条认证到资格/权益业务链和一条活动报名链。
- 验证撤权、过期机器凭据、跨项目资源请求仍被拒绝，观察错误率、外部依赖、队列重试与失败记录。
- 确认真实 SQL 连接和 S3 对象读取，检查恢复之后的文件版本与权限。SMTP 接收协议成功不等于入箱；需要收件侧证据。
- 记录新 image digest、实际迁移版本、发布时刻与检查结果，解除维护并恢复外部写入口。保留回退点到观察期结束。

没有真实域名、OIDC 客户端、服务器或外部服务凭据时，可以完成代码与隔离自动化验收；真实部署项继续标为待验收，不以测试 issuer 或空资源页面替代。

## 回退

升级后出现不可接受问题时，首先挂维护页，停止新请求/设备任务与外部写入并保存故障日志。若升级后已有新业务数据，先备份现场，明确恢复旧点会丢失哪些变更以及如何补偿。

1. 停止后端，保存当前数据卷，避免原地覆盖或删 WAL。
2. 验证升级前备份及同一主密钥，用 `platform_backup.py restore` 恢复到全新目录/卷。
3. 将 SQL/S3 切回同一协调恢复点，恢复对应角色/权限/版本；仅恢复控制面会造成资源状态与真实数据不一致。
4. 使用升级前镜像和配置，将 Compose 的数据挂载切换到新恢复卷；旧卷保持不动。
5. 在限制外发的状态下完成就绪、身份、记录、文件、权限和设备检查，重新应用备份之后的撤权，然后恢复流量。

逐项记录实际耗时和缺失数据。回退过程中恢复了发送队列、事件执行记录和历史会话，应核对已投递通知及已执行外部动作，防止重复执行。没有跨数据面的原子回滚能力时，保持维护状态并由负责人完成差异对账，不能宣称无损回退。
